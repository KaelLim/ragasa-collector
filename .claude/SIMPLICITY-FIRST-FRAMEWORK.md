# 簡單性優先決策框架 v1.0

## 🎯 **簡單性優先核心原則**

### **📐 簡單性定義標準**

```markdown
【技術簡單性】
✅ 簡單：單一功能，清晰邏輯，最少依賴
❌ 複雜：多重責任，嵌套邏輯，重依賴

【架構簡單性】  
✅ 簡單：線性流程，明確接口，標準模式
❌ 複雜：迴環依賴，模糊邊界，創新模式

【配置簡單性】
✅ 簡單：最少配置項，合理預設，明確文檔
❌ 複雜：大量選項，無預設值，缺乏說明

【使用簡單性】
✅ 簡單：一鍵啟動，零配置，直觀操作
❌ 複雜：多步驟，需配置，學習成本高
```

### **⚖️ 複雜性評估矩陣**

```
複雜性評分 (1-10)：

【1-3 分：簡單】
- 可在 5 分鐘內向他人解釋
- 依賴項目少於 3 個
- 配置步驟少於 3 步
- 單一檔案可包含核心邏輯

【4-6 分：適中】  
- 需要 10-15 分鐘解釋
- 依賴項目 3-5 個
- 配置步驟 3-5 步
- 需要 2-3 個檔案協作

【7-10 分：複雜】
- 需要超過 20 分鐘解釋
- 依賴項目超過 5 個
- 配置步驟超過 5 步
- 需要複雜的檔案結構

🚨 **決策規則**：僅當複雜性帶來的價值 > 複雜性成本時，才接受複雜方案
```

## 🔍 **決策框架：SIMPLE 方法論**

### **S - Scope 範圍界定**

```markdown
【範圍明確化檢查】
1. 核心需求是什麼？（一句話描述）
   答案：_____

2. 邊界條件在哪裡？
   - 必須支援：_____
   - 可以不支援：_____
   - 明確排除：_____

3. 成功標準是什麼？
   - 最小可行標準：_____
   - 理想標準：_____
   - 過度設計邊界：_____

【範圍控制原則】
✅ 優先滿足 80% 的常見需求
❌ 避免為 20% 的邊緣情況增加複雜性
```

### **I - Identify 識別選項**

```markdown
【方案識別清單】
1. 最簡單方案（最小功能實現）
   - 描述：_____
   - 優點：_____
   - 限制：_____

2. 標準方案（平衡功能與複雜性）
   - 描述：_____
   - 優點：_____
   - 限制：_____

3. 完整方案（全功能實現）
   - 描述：_____
   - 優點：_____
   - 限制：_____

【識別規則】
- 至少產生 3 個不同複雜度的方案
- 優先考慮業界標準解決方案
- 避免「創新」除非確有必要
```

### **M - Measure 測量評估**

```markdown
【量化評估表】

| 評估維度 | 簡單方案 | 標準方案 | 完整方案 | 權重 |
|----------|----------|----------|----------|------|
| 開發時間 | __/10    | __/10    | __/10    | 25%  |
| 維護成本 | __/10    | __/10    | __/10    | 20%  |
| 使用簡易度 | __/10  | __/10    | __/10    | 20%  |
| 需求覆蓋度 | __/10  | __/10    | __/10    | 15%  |
| 擴展性   | __/10    | __/10    | __/10    | 10%  |
| 穩定性   | __/10    | __/10    | __/10    | 10%  |

加權總分 = Σ(評分 × 權重)

【評估原則】
- 簡單性相關維度（開發時間、維護成本、使用簡易度）佔總權重 65%
- 功能性維度（需求覆蓋、擴展性、穩定性）佔總權重 35%
```

### **P - Prefer 偏好選擇**

```markdown
【選擇決策樹】

1. 簡單方案能滿足核心需求嗎？
   ✅ 是 → 選擇簡單方案
   ❌ 否 → 繼續評估

2. 標準方案的額外複雜性是否必要？
   ❌ 否 → 優化簡單方案
   ✅ 是 → 選擇標準方案

3. 完整方案的價值是否顯著超過複雜性成本？
   ❌ 否 → 選擇標準方案
   ✅ 是 → 謹慎考慮完整方案

【偏好順序】
1st: 簡單方案（滿足核心需求）
2nd: 優化的簡單方案（增加必要功能）
3rd: 標準方案（平衡複雜性）
Last: 完整方案（僅當價值明確超過成本）
```

```markdown
   - 實際使用體驗：_____

   - 簡化機會：_____

2. 長期觀察（1 個月後）
   - 維護負擔：_____
   - 功能需求變化：_____
   - 架構演進方向：_____

3. 決策優化
   - 當初選擇是否正確？_____
   - 下次類似決策的改進點：_____
   - 框架本身的優化建議：_____
```

### **E - Execute 執行實施**

```markdown
【執行階段檢查】

1. 實施前最後確認
   - [ ] 方案符合 SIMPLE 框架評估結果
   - [ ] 已考慮更簡單的替代方案
   - [ ] 複雜性確實帶來對應價值
   - [ ] 有明確的簡化路徑（如需要）

2. 實施過程監控
   - [ ] 實際複雜性未超出預期
   - [ ] 開發過程中未增加不必要功能
   - [ ] 保持對原始目標的專注

3. 完成後驗證
   - [ ] 最終結果符合簡單性目標
   - [ ] 使用者確認解決方案有效
   - [ ] 記錄經驗供後續參考
```

## 🎯 **常見場景決策指南**

### **📡 API 整合場景**

```markdown
【API 整合複雜性決策】

場景：整合第三方 API 服務

簡單方案：
- 直接 HTTP 請求
- 基本錯誤處理
- 同步呼叫

標準方案：
- SDK 包裝
- 重試機制
- 異步處理

複雜方案：  
- 自建抽象層
- 多 API 聚合
- 快取與優化

決策因子：
✅ API 調用頻率 < 100/小時 → 簡單方案
✅ 標準業務需求 → 標準方案  
⚠️ 特殊整合需求 → 評估複雜方案
```
